# VpnClient

An Android VPN client built on the WireGuard protocol. The cryptographic
core is written in Rust ([BoringTun](https://github.com/cloudflare/boringtun),
Cloudflare's WireGuard implementation) and connected to Kotlin through
[UniFFI](https://mozilla.github.io/uniffi-rs/) (autogenerated bindings, no
manual JNI).

## What's demonstrated here

- A Rust crate (`rust/vpn-core`) with real x25519 cryptography and a full
  WireGuard handshake (not a stub — it uses the actual protocol library).
- A UniFFI bridge: Rust `struct`/`enum`/objects automatically become Kotlin
  `data class`/`sealed class`/classes with `close()`.
- Cross-compilation for Android (`arm64-v8a`, `x86_64`) via `cargo-ndk`.
- A real `android.net.VpnService`: establishes a TUN interface, encrypts
  outgoing traffic and decrypts incoming traffic through the Rust core.
- `protect()` on the UDP socket — without it, the VPN would route itself
  back through its own tunnel in an infinite loop.

## How to run (zero setup required)

1. Open in Android Studio, wait for Gradle sync.
2. Run on an emulator or device.
3. Tap **"Self-test (offline, no server)"**.

The app creates two independent `WireguardTunnel` objects ("client" and
"server") entirely within itself and runs a real cryptographic handshake
between them, step by step, with the actual bytes of every packet. This
proves the whole Rust → UniFFI → Kotlin pipeline works, with no
infrastructure to stand up.

## Connecting to a real server

The **"Connect to server"** button drives a full `VpnService` with a TUN
interface and requires a real WireGuard endpoint. The repository includes a
minimal test server:

```bash
cd rust/vpn-core
cargo run --bin test_server -- 51999
```

It listens on the given port with a hardcoded key pair (see
`src/bin/test_server.rs` and `VpnConfig` in
`data/.../DefaultTunnelRepository.kt` — they must match). From the Android
emulator, the server on the host machine is reachable at `10.0.2.2`.

## Architecture: multi-module

The project is split into independent Gradle modules with an enforced
dependency direction — the same way teams structure a codebase so multiple
developers can work on different features in parallel without conflicts:

```
VpnClient/
├── domain/            pure Kotlin, NO Android SDK. Models, interfaces
│                       (TunnelRepository, TunnelStatusReporter), nothing else.
├── data/               implementation of the domain interfaces: WireguardVpnService,
│                       DefaultTunnelRepository, UniFFI bindings, the .so from rust/.
├── feature-selftest/   the self-test screen (Compose + ViewModel). Depends only on :domain.
├── feature-connect/    the server-connect screen. Also depends only on :domain.
├── app/                thin module: Koin DI, NavHost with deep links, the manifest.
├── rust/vpn-core/       the Rust crate with the cryptography (WireGuard via boringtun).
└── jniLibs/             compiled .so files for Android (arm64-v8a, x86_64).
```

Dependency direction: `feature-*` and `data` depend on `domain`, never the
other way around. `feature-*` never depends on `data` directly — the
concrete implementation (`DefaultTunnelRepository`) is wired in by Koin in
`app/VpnClientApp.kt`. This means `feature-selftest` can be tested without
Android or Rust — just swap in a fake `TunnelRepository`.

`WireguardVpnService` cannot call into UI code directly — instead, it
reports status through `TunnelStatusReporter` (the same object as
`TunnelRepository`, just a different interface), and the UI learns about
changes through a `StateFlow` without knowing the service exists.

**The presentation layer is strict MVI**, not MVVM with direct method calls:
the UI dispatches an `Intent` (`viewModel.onIntent(SelfTestIntent.RunSelfTest)`,
`viewModel.onIntent(ConnectIntent.Connect)`) instead of calling ViewModel
methods directly. Each screen's state is a single object (`SelfTestUiState`,
`ConnectionState`), not scattered fields. One deliberate exception: the
system `VpnService.prepare()` dialog stays in the Composable (it needs an
Activity context) — the user's actual intent only reaches the ViewModel
after that platform-level consent step is confirmed.

**Deep links:** `vpnclient://selftest` and `vpnclient://connect` open a
specific screen directly, bypassing in-app navigation — the same way real
features open one another by link without knowing each other's internals.

## Rust core tests

```bash
cd rust/vpn-core
cargo test
```

Among the tests: a full handshake between two in-memory tunnels, and
separately, a handshake over real UDP sockets on loopback (proving the API
is suited to real network I/O, not just passing bytes in memory).

## Tech stack

Kotlin, Jetpack Compose, Rust, [boringtun](https://github.com/cloudflare/boringtun),
[UniFFI](https://github.com/mozilla/uniffi-rs), `cargo-ndk`, `android.net.VpnService`.
